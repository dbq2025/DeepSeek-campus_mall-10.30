# 阶段 1 · 领域决策：订单状态机 + 规格与库存

> 这两项决定数据模型骨架，改动代价随开发推进指数上升，因此必须在写第一行代码前定死。
> 结论先行：**订单 5 状态、只前进不回退**；**商品不做真 SKU，做「展示型轻量规格」**；**库存做，单维、下单即扣、条件更新防超卖**。

---

## 一、订单状态机

### 1.1 状态定义（5 个，无退款态）

| code | 枚举名 | 中文 | 含义 | 终态 |
|---|---|---|---|---|
| 0 | `PENDING_PAYMENT` | 待付款 | 已下单，库存已扣，等待支付 | 否 |
| 1 | `PENDING_SHIPMENT` | 待发货 | 已付款，等待管理员发货 | 否 |
| 2 | `PENDING_RECEIPT` | 待收货 | 已发货，等待用户确认 | 否 |
| 3 | `COMPLETED` | 已完成 | 用户确认收货 | **是** |
| 4 | `CANCELLED` | 已取消 | 用户取消或超时未付款，库存已回补 | **是** |

**为什么没有「已退款」「退款中」**：退款涉及资金反向流转、部分退款金额计算、退款单与订单的一对多关系，是完整电商系统里工作量排名前三的模块，而两份报告的功能清单里均未出现。留一个退款态却不做退款逻辑，比没有更糟——答辩时会被追问资金链路。**范围外即明确不做**，写进文档比藏着好。

### 1.2 合法迁移（5 条，全部单向）

| # | from → to | 触发者 | 接口 | 前置条件 | 副作用 |
|---|---|---|---|---|---|
| T1 | 0 → 1 | 注册用户 | `POST /front/orders/{id}/pay`（模拟支付） | 订单属于当前用户；`status=0`；未超时 | 写 `pay_time`；`pay_amount=total_amount` |
| T2 | 0 → 4 | 注册用户 | `POST /front/orders/{id}/cancel` | 同上，`status=0` | 回补库存；写 `cancel_time`、`cancel_reason='用户取消'` |
| T3 | 0 → 4 | 系统 | 定时任务（每 5 分钟） | `status=0` 且 `create_time < now-30min` | 同上，`cancel_reason='超时未付款'` |
| T4 | 1 → 2 | 管理员 | `PUT /admin/orders/{id}/ship` | `status=1` | 写 `ship_time`、`tracking_no`（可空） |
| T5 | 2 → 3 | 注册用户 / 管理员 | `PUT /front/orders/{id}/confirm`｜`PUT /admin/orders/{id}/confirm` | `status=2`；用户侧需归属校验 | 写 `finish_time` |

### 1.3 禁止迁移（负向规则，同样是设计的一部分）

| 禁止 | 原因 |
|---|---|
| 1 → 4、2 → 4 | 已付款/已发货不能直接取消，须走退款，退款不在范围内 |
| 0 → 2、0 → 3、1 → 3 | 不允许跳级，跳级意味着"未付款就发货"这类资损漏洞 |
| 3 → 任意、4 → 任意 | 终态不可变更 |
| 任意 → 更小 code | 状态只增不减，不做回退 |

实现层面不写 `if-else` 堆叠，用一张**允许迁移表**（`Map<Status, Set<Status>>`）集中判定，非法迁移统一抛 `3002 状态不允许`。新增状态时只改这张表，不改业务代码。

### 1.4 幂等与并发

所有迁移统一用**条件更新**，不先查后改：

- `UPDATE orders SET status = :to, ... WHERE id = :id AND status = :from`
- 影响行数为 0 → 说明状态已被别的请求改过：若当前已是目标态，按成功返回（幂等）；否则返回 `3002`。
- 理由：用户双击"支付"、定时任务与手动取消并发，是这类项目最典型的重复扣减/重复回补场景。条件更新一行 SQL 就能封死，不需要分布式锁。

### 1.5 超时取消的实现取舍

用 Spring `@Scheduled(fixedDelay = 300000)` 扫表，批量取 100 条循环处理，**不引入 MQ 延迟队列、不引入 XXL-Job**。理由：单机教学项目，量级在千级订单以内；引入 MQ 只为演示延迟消息，会让部署复杂度和故障面翻倍。文档里写明这是"有意的简化"，比假装是分布式系统更专业。

### 1.6 表结构要点（`orders`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | bigint | 雪花 ID，返回前端转 String |
| `order_no` | varchar(32) | 业务单号，唯一索引，`yyyyMMddHHmmss` + 6 位随机 |
| `user_id` | bigint | 下单用户，普通索引 |
| `total_amount` | decimal(10,2) | 商品总额 |
| `pay_amount` | decimal(10,2) | 实付金额，未支付时 = total_amount |
| `status` | tinyint | 0–4，与枚举一一对应 |
| `receiver_name` / `receiver_phone` / `receiver_address` | varchar | **下单时快照**，用户改地址不影响历史订单 |
| `remark` | varchar(200) | 买家留言 |
| `tracking_no` | varchar(50) | 发货单号，可空 |
| `create_time` / `pay_time` / `ship_time` / `finish_time` / `cancel_time` | datetime | 每个状态迁移各写各的时间，便于统计与对账 |
| `cancel_reason` | varchar(50) | 用户取消 / 超时未付款 |
| `deleted` | tinyint | 逻辑删除，0/1 |

**不设 `update_time` 自动更新语义以外的触发器**，状态变更时间一律显式写入——否则统计"平均发货时长"时拿不到准确时点。

## 二、规格决策：不做真 SKU，做「展示型轻量规格」

### 2.1 需求证据（决策的事实基础）

- 前端报告 1.3「商品详情：商品信息展示、**规格选择**、加入购物车 / 立即购买 / 收藏」——只出现四个字，未定义规格维度。
- 后端报告全篇（1.3 功能需求、2.3 数据库设计、3.2 模块实现）**零次**提及 SKU、多规格、规格库存。
- 后端 2.3 要求"说明核心实体间的关联关系（一对多、多对多、一对一）"——现有 7 张表已能覆盖三种关系，加 SKU 只为凑表数，不产生新的教学价值。

结论：规格是**前端交互层的诉求**，不是后端的领域约束。

### 2.2 三个候选方案

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| A 真 SKU | 新增 `product_sku`，价格/库存下沉到 SKU，购物车与订单明细指向 SKU | 高：多 1 张表 + 规格组合生成 + 加购/下单/库存/统计四处改造，工作量约 2.5–3 倍 | 高：SKU 组合丢失、库存对不齐、统计需改按 SKU 聚合，答辩难自圆其说 |
| **B 展示型轻量规格（采用）** | `product.spec_json` 存规格项定义；加购/下单时把用户选择存为 `spec_text` 快照；价格与库存仍按商品维度 | 低：2 个字段 + 1 个选择器组件 | 低：规格不影响价格，属可解释的范围裁剪 |
| C 完全不做 | 详情页不出现规格选择 | 最低 | 中：与前端报告 1.3 明确冲突，功能点缺失会被扣分 |

### 2.3 采用方案 B 的具体形态

- `product.spec_json`（varchar 500，可空）：形如 `[{"name":"颜色","values":["曜石黑","月光白"]},{"name":"尺码","values":["M","L","XL"]}]`。为空表示该商品无规格，详情页隐藏选择器。
- `cart.spec_text` / `order_item.spec_text`（varchar 100，可空）：形如 `颜色:曜石黑;尺码:M`，**下单时快照**。
- 校验规则：有 `spec_json` 的商品，加购必须提交与定义匹配的规格组合；无 `spec_json` 的商品，提交规格视为参数错误。
- 购物车唯一键改为 `(user_id, product_id, spec_text)`——同一商品不同规格算不同行，这跟"不做 SKU"并不冲突：行内仍按商品计价。

### 2.4 逃生通道（若老师要求真 SKU）

改造点收敛在 3 处，不推翻现有设计：

1. 新增 `product_sku` 表（`product_id`、`spec_text`、`price`、`stock`、`sku_code`）。
2. `cart` / `order_item` 增 `sku_id`、`sku_price`，`spec_text` 保留（作冗余展示）。
3. 库存扣减从 `product` 移到 `product_sku`，其余（订单状态机、事务边界、接口形态）不变。

因为**快照字段从第一天就有**，这次升级不需要数据迁移脚本，也不会让历史订单失真。这就是选 B 而不是 C 的额外收益。

## 三、库存决策：做，单维，下单即扣

### 3.1 为什么做

库存是"事务控制 + 并发安全"唯一天然的教学载体。报告 3.2 明确要求"订单创建、状态流转、**事务控制保证数据一致性**"，4.3 要求"并发访问优化"。没有库存，这个技术点就只剩空话。反之，有了 `stock`，"超卖"可以在测试章节用两行并发脚本实证，是答辩的硬通货。

### 3.2 扣减时点：下单扣，不是支付扣

| 时点 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 下单扣（采用） | 库存占用直观，未付款订单可超时释放；超卖在单机并发下就能复现，测试可覆盖 | 需要超时回补逻辑 | **采用** |
| 支付扣 | 无需回补 | 未付款订单不占库存，超卖只在并发支付时暴露，测试难构造，问题藏得深 | 不采用 |

### 3.3 防超卖的实现契约

```sql
UPDATE product SET stock = stock - #{n}
WHERE id = #{id} AND stock >= #{n} AND status = 1
```

影响行数为 0 → 抛 `3001 库存不足`，整个下单事务回滚（订单主表、明细、购物车清理一并撤销）。**禁止**"先 `select stock` 再判断再 `update`"，那是本项目的头号事故写法。多商品下单按 `product_id` 升序加锁，避免交叉死锁。

### 3.4 四条边界规则

1. **加购不校验库存**：购物车是"意向清单"，只在详情页展示"仅剩 N 件"提示。
2. **下单校验库存 + 商品状态**：`status != 1`（已下架）时禁止下单，返回 `3005 商品已下架`。
3. **回补只在 T2/T3 成功的那一次执行**：靠条件更新 `status 0 → 4` 的影响行数保证只回补一次，不做"先查状态再回补"。
4. **取消后商品已下架仍要回补**：库存回补不判断商品状态，否则库存会永久丢失。

## 四、连带影响清单（后续阶段必须同步）

| 层面 | 受影响项 |
|---|---|
| 表结构 | `orders`（+4 时间字段、cancel_reason、tracking_no）；`order_item`（+product_name、price、picture、spec_text 四个快照字段）；`product`（+stock、spec_json、status）；`cart`（+spec_text，唯一键三元组） |
| 接口 | 新增 `pay` / `cancel` / `ship` / `confirm` 四个动作型接口；商品详情出参含 `stock` 与 `specJson`；订单列表出参含 `statusText` 与可执行动作列表 `actions[]` |
| 页面 | 详情页规格选择器（无规格时隐藏）；订单列表按状态渲染不同按钮；后台订单页"发货"仅在 `status=1` 出现 |
| 测试 | 状态机用例 5 条合法 + 5 条非法；超卖用例（并发 2 单抢最后 1 件）；取消回补后库存一致性校验 |
| 文档 | 契约表需标注每个动作接口的合法源状态；数据字典需写明 `status` 枚举取值 |
