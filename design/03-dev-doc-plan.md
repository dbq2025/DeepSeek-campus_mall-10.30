# 阶段 3 · 开发文档规划

> 定位：这份规划管的是**开发过程中真正会被反复查阅的文档**，不是交作业的报告。
> 三条原则：① 只写"会变的东西"；② 每个事实只在一处定义（单一事实来源）；③ 文档随开发增量回填，不做"最后统一补"。
> 总量控制：**7 份，合计 ≤ 60 页**。超过这个量，一定是在写没人看的东西。

## 二、核心文档：30-接口契约

这是整个项目投入产出比最高的一份。**它写扎实，后面五个阶段的返工量下降一个数量级；跳过它，会用三倍时间在"字段对不上"上。**

### 2.1 单条接口的固定模板（12 个字段，一个都不能省）

| 字段 | 说明 | 示例 |
|---|---|---|
| 编号 | `模块-序号`，全局唯一，用于代码注释与用例引用 | `ORD-03` |
| 名称 | 动宾短语 | 取消订单 |
| 方法 + 路径 | 含 `/api` 前缀 | `POST /api/front/orders/{id}/cancel` |
| 鉴权 | 游客 / 登录用户 / 管理员 / 需归属校验 | 登录用户 + 归属校验 |
| 请求参数 | 位置（path/query/body）+ 名称 + 类型 + 必填 + 约束 | body: `reason` string 否 ≤50 |
| 成功响应 data | 精确到字段名与类型 | `null` |
| 失败码 | 该接口可能返回的业务码 | 3002 / 3003 |
| 副作用 | 写哪些表、改哪些字段 | `orders.status=4`、`product.stock += n` |
| 前置条件 | 状态机前置 | `status=0` 且属于当前用户 |
| 对应页面 | 页面名 + 触发位置 | 我的订单 / 取消按钮 |
| 对应报告章节 | 让文档与报告可双向追溯 | 后端 3.2-4 订单管理 |
| 状态 | 待实现 / 已实现 / 已联调 | 已联调 |

### 2.2 分组与规模预估（约 40 个接口）

| 分组 | 前缀 | 预估数量 | 备注 |
|---|---|---|---|
| 认证 | `/auth` | 3 | 注册、用户登录、管理员登录 |
| 分类（后台） | `/admin/categories` | 5 | 分页、全量、增、改、删 |
| 商品（后台） | `/admin/products` | 6 | 分页条件查、详情、增、改、删、批量上下架 |
| 订单（后台） | `/admin/orders` | 4 | 分页、详情、发货、代确认 |
| 统计（后台） | `/admin/stats` | 2 | 月销量、分类订单占比 |
| 商品（前台） | `/front/products` `/front/categories` | 3 | 列表搜索、详情、分类树 |
| 购物车 | `/front/cart` | 5 | 列表、加购、改数量、删一项、清空 |
| 订单（前台） | `/front/orders` | 6 | 下单、列表、详情、支付、取消、确认收货 |
| 收藏 | `/front/favorites` | 3 | 添加、取消、列表 |
| 文件 | `/admin/files` | 1 | 图片上传（返回相对路径） |

### 2.3 写契约的三条硬规则

1. **字段名先定，代码后写**。前端 mock、后端 entity/VO、测试断言全部照抄这一个名字，不允许出现 `productName` / `product_name` / `name` 三种写法。
2. **每个接口必须能指到一个页面上的具体点击**。指不到的接口，要么是多余设计，要么是漏了页面。
3. **动作型接口必须写"前置状态"**。订单类接口不写前置状态，等于埋了"已发货还能取消"的雷。

## 三、其余六份的内容大纲

### 10-需求与范围（8 页）

1. 角色与权限矩阵（3 角色 × 约 10 组接口，标注"需归属校验"的格子）
2. 功能清单 40–55 条，五要素：谁用 / 前置 / 主流程 / 异常分支 / 验收标准
3. 页面清单（前后台 18–20 个）+ 路由路径 + 归属子系统
4. 术语与枚举字典（`product` 唯一叫法、订单状态 0–4、上下架 0/1）
5. **范围外清单**（支付、物流轨迹、退款、优惠券、评价、多仓、真 SKU）+ 一句话理由
6. 与两份报告章节的对照表

### 20-领域模型与数据库（10 页）

1. E-R 图（7 实体，标注一对多/多对多，满足报告 2.3 要求）
2. 7 张表逐表结构：字段、类型、约束、默认值、注释
3. 索引设计说明（唯一键：`user.username`、`orders.order_no`、`cart(user_id,product_id,spec_text)`、`favorite(user_id,product_id)`；普通索引：`product.category_id`、`orders.user_id`、`orders.status`）
4. 设计取舍说明（为什么订单明细存快照、为什么金额用 decimal、为什么逻辑删除只加在 orders/product）
5. `schema.sql` 与 `data.sql` 的维护约定（两者是本文档的可执行副本，改表先改文档再改脚本）

### 40-页面与交互（10 页）

1. 路由表：路径 / 组件 / 是否需要登录 / 是否需要管理员（对应报告 2.3）
2. 页面-接口映射表：每个页面调哪几个接口，按调用顺序排（首屏、交互、提交）
3. 每页四态描述：loading / empty / error / 正常，各写一句话
4. 组件清单：`BaseTable` `BaseDialog` `BasePager` `ImageUpload` `EmptyState` `StatusTag` `SpecSelector`，各自 props/事件/使用页面
5. 布局与配色规范（后台密集、前台留白；主色、字号、间距三档）

### 50-环境与运行（4 页）

1. 版本清单（照抄 `00-env-inventory.md`，不重复维护结论）
2. 启动步骤：切 JDK 17 → 建库导表 → 起后端 → 起前端 → 默认账号
3. 配置项说明：数据库、JWT 密钥、上传目录、mock 开关
4. 故障速查表（≥8 条）：`JAVA_HOME` 未切、`factoryBeanObjectType` 报错、时间偏 8 小时、401 循环跳转、跨域、图片 404、分页失效、雪花 ID 精度丢失

### 60-测试与验收（6 页）

1. 用例表模板：编号 / 模块 / 前置 / 步骤 / 预期 / 实际 / 结论 / 对应接口编号
2. 覆盖矩阵：40 个接口 × 正常/边界/异常三类，标出必测项（状态机 10 条、库存 4 条、权限 6 条）
3. 并发与性能：超卖复现步骤、统计接口耗时记录
4. 缺陷记录：发现 / 定位 / 修复 / 回归
5. 与报告 4.1–4.4 的对应关系（测一条填一行，禁止最后补）

### 90-进度看板（2 页）

一张表：模块 / 页面 / 接口编号 / 状态（未开始·进行中·已实现·已联调）/ 对应报告章节 / 备注。
**每完成一个单元当场更新**——这张表既是进度，也是答辩时的讲解提纲。

## 五、契约变更流程（防返工的闸门）

1. **提出**：写清"谁需要、为什么、不改会怎样"。
2. **评估影响面**：受影响的页面、mock 文件、后端 service、测试用例、报告章节，列成清单。
3. **一次改完，一次提交**：契约 → mock → 前端 `api/*.js` → 后端 controller/service → 用例，同一批改动，不留半成品。
4. **打版本号**：`v1.0 → v1.1`，在文件头写 Changelog（日期 / 变更条目 / 影响接口编号）。
5. **禁止"代码先改、文档后补"**：一旦发生，契约表就失去权威性，后面所有 AI 对话都会基于错误事实展开。

**两个学期之间的衔接**：前端阶段结束时冻结 `30-接口契约 v1.0` + `mock/` 一起归档。第 2 学期开工第一件事是复活这份 mock 与契约，而不是凭记忆重建。

## 七、执行顺序（阶段 3 之后立刻做什么）

1. 先写 `30-接口契约` 的**认证 + 商品 + 购物车**三组（约 15 个接口），这三组是前端开工的最小集。
2. 同步写 `20-领域模型`，产出 `schema.sql`（可执行，能建库）。
3. 再补 `10-需求与范围`（此时功能边界已经清楚，写得最快）。
4. `40-页面与交互` 与前端开发同步推进，每页开工前补该页那一行映射。
5. `60-测试与验收` 从第一个接口联调成功那天开始填，不提前，也不延后。
