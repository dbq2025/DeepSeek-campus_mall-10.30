## 1. 计划目标与执行策略

### 1.1 目标

在**接口契约先行**的前提下，完成校园电商平台前台的 19 个页面、2 套布局、7 个通用组件与 2 个 Pinia store，并以自写 Mock 打通「浏览—搜索—详情—加购—下单—查询订单」与后台「类型—商品—订单—统计」两条完整链路。交付物必须可构建、可演示、可追溯到报告章节。

### 1.2 执行策略

```
契约先行 → 工程底座 → 前台浏览 / 账户 → 交易闭环 → 后台商品域 → 后台订单与统计 → 验收归档
```

三条贯穿全程的规则：

1. **一批一次验收**：每批以 `npm run build` + 四态（loading / empty / error / 正常）为门禁，未通过不进入下一批。
2. **一批一次提交**：提交格式 `feat(front): ...`，保证任意一步可回滚。
3. **契约是唯一事实来源**：`api/*.js`、Mock、页面字段全部从 `design/30-接口契约.md` 派生，禁止"先写代码、后补契约"。

### 1.3 本阶段不做真实联调

后端当前仅有 `common` 层与 `/api/health`，业务接口尚未实现。因此本阶段以 **Mock 驱动验收**，`.env.development` 的 `VITE_USE_MOCK=false` 只保留开关与联调清单，真实联调放在阶段 5。

## 5. 界面结构与路由

### 5.1 路由设计原则

- 三组前缀：`/`（前台）、`/admin`（后台）、`/dev`（开发工具，不进导航）。
- 所有页面组件**懒加载**，`meta` 统一携带 `{ title, requiresAuth, requiresAdmin }`。
- 守卫只做"藏"，真正的权限边界在后端；`/admin/**` 额外校验 `role === 'ADMIN'`。
- 前台登录页与后台登录页**分开**：`/login` 与 `/admin/login`，互不复用，避免登录后跳错子系统。
- 订单详情属"我的订单"，前端只隐藏入口，归属校验由后端完成。

## 6. 组件划分

### 6.1 通用组件（`src/components/`）

只放**无业务语义**的组件，props 必须显式声明类型与默认值。

| 组件 | 职责 | 关键 props / 事件 | 使用页面 |
|---|---|---|---|
| `BaseTable` | 列配置渲染、四态、操作列插槽 | `columns`、`data`、`loading`、`error`；`@retry` | 4 个后台列表 + 订单列表 |
| `BasePager` | 分页 | `v-model:page`、`v-model:size`、`total` | 所有分页页 |
| `BaseDialog` | 表单弹窗 | `v-model`、`title`、`confirm-loading`；`@confirm` | 类型管理、发货 |
| `ImageUpload` | 上传、预览、删除、大小限制 | `v-model:url`、`limit=2MB` | 商品新增/编辑 |
| `EmptyState` | 空态与错误态 | `type=empty/error`、`title`、`desc`；`@retry` | 全部列表页 |
| `StatusTag` | 状态到文案与颜色的映射（集中一处） | `status`、`type=order/product` | 订单、商品 |
| `SpecSelector` | 规格选择并生成 `spec_text` | `specJson`、`v-model`、完整性校验 | 商品详情 |

### 6.2 业务组件（留在 `views/**/components/`）

| 组件 | 所在目录 | 职责 |
|---|---|---|
| `ProductCard` | `views/front/components/` | 商品卡：主图、名称、价格、库存提示、加购入口 |
| `SpecEditor` | `views/admin/product/components/` | `spec_json` 可视化编辑 + JSON 合法性校验 |

### 6.3 组件约束

- 通用组件**不发请求**、不读 store，数据与行为由父级传入。
- 业务组件允许读 store，但不得直接 `axios`。
- 组件内不写业务计算（总价、库存判断、状态可流转性一律以后端为准）。
- 图标按钮必须带 `aria-label`；图片必须有 `alt`。

## 7. 状态与数据流

### 7.1 Store 设计

| store | 内容 | 关键动作 | 持久化 |
|---|---|---|---|
| `user` | `token`、`profile`、`role` | `login()`、`logout()`、`isAdmin` getter | `localStorage`：`mall_token`、`mall_user` |
| `cart` | **仅角标数量** `count` | `refresh()`、`increase(n)`、`decrease(n)`、`clear()` | 不持久化，登录后重新拉取 |

- `cart.count` 由 `GET /front/cart` 求和得出（`sum(quantity)`），**不缓存购物车列表**，列表永远以服务端为准。
- 不引入 Pinia 持久化插件，手写两个 key，避免新增依赖。

### 7.2 列表页数据流

```
页面 query（page/size/keyword/status…）
  → useListQuery(fetcher, initQuery)
  → api/xxx.js（标注契约编号）
  → utils/request.js（解包 data、统一错误）
  → Mock 或后端
  → { list, total, loading, error }
  → BaseTable / EmptyState / BasePager
```

- `useListQuery` 约 60 行，统一产出 `query / list / total / loading / error / load / reset`，供 8 个列表页复用（决策 D4）。
- 查询条件变化时重置到第 1 页；删除最后一页最后一条后自动回退一页。

### 7.3 请求层（`utils/request.js`）

- 响应统一**解包 `data`**，页面拿到的是业务数据，不再判断 `code`。
- 认证类：`401 / 2001 / 2002` → 清 `mall_token`、`mall_user`、重置 store → 按当前路径跳 `/admin/login` 或 `/login?redirect=`。
- 权限类：`2003` → 提示"没有操作权限"，不跳转。
- 业务类：`3001 / 3002 / 3003 / 3004 / 3005` → 直接展示后端 `msg`，前端不重写文案。
- 同屏只弹一条错误提示，避免并发请求刷屏。
- 超时 10s；不做自动重试（避免重复下单）。

### 7.4 路由守卫

- `beforeEach`：设置 `document.title`；校验 `requiresAuth` 与 `requiresAdmin`。
- 未登录访问受保护页 → `/login?redirect=fullPath`；管理员页 → `/admin/login?redirect=fullPath`。
- 已登录用户访问登录页 → 回首页或 `redirect`。
- 守卫**不做**接口调用，角色信息取自 `mall_user`；令牌失效由 401 拦截器兜底。

### 7.5 两条硬规则

1. **订单动作按钮只渲染后端返回的 `actions[]`**（`design/01` §4 已定），前端不写 `if (status === 0)` 之类的状态机分支。
2. **金额与 ID 全链路字符串**：不做 `parseInt(id)`、不做浮点加减；页面上的"合计"只是选中项预览，最终金额以下单返回与订单详情为准。

## 8. 接口对接与 Mock

### 8.1 api 目录约定

```
src/api/
├── auth.js                 AUTH-01…03
├── product.js              FPRD-01…03
├── cart.js                 CART-01…05
├── order.js                FORD-01…06
├── favorite.js             FAV-01…03
└── admin/
    ├── category.js         CAT-01…05
    ├── product.js          PRD-01…06
    ├── order.js            ORD-01…04
    ├── stat.js             STAT-01…03
    └── file.js             FILE-01
```

- 每个导出函数上方用一行注释标注契约编号，便于报告与测试用例反查。
- 页面只 import api 函数，**禁止**在 `.vue` 中直接 `axios`。
- 参数命名与契约完全一致，不做前端侧改名。

### 8.2 Mock v2 能力

| 能力 | 说明 |
|---|---|
| 路由匹配 | 支持 `:id` 路径参数、query、JSON body |
| 延迟 | 150–300ms，模拟真实网络，暴露 loading 态问题 |
| 有状态 | 内存中真实下单、扣库存、回补、改状态，整条闭环可演示 |
| 复位 | `POST /api/__mock/reset` 重置数据集，便于反复演示 |
| 异常场景 | 内置 `stock=1` 商品、非法状态迁移、已下架商品，覆盖 3001/3002/3005 |
| 文件上传 | 返回本地占位图路径，不依赖外网 |
| 契约对齐 | 每条路由标注契约编号，字段名与契约逐字一致 |

### 8.3 契约变更流程

严格按 `design/03-dev-doc-plan.md` §5 执行：

1. 提出变更理由与影响面（页面、Mock、api、后端、用例）。
2. 一次改完：契约 → Mock → `api/*.js` → 页面。
3. 契约文件头打版本号并写 Changelog。
4. **禁止**代码先改、文档后补。

### 8.4 环境切换

| 环境 | 文件 | `VITE_USE_MOCK` | 说明 |
|---|---|---|---|
| 开发 | `.env.development` | `true` | Mock 中间件拦截 `/api/**` |
| 生产 | `.env.production` | `false` | 同源 `/api`，由部署层转发 |

切换只改环境变量，不改业务代码。

## 10. 构建与工程规范

### 10.1 依赖与构建

- 依赖冻结：本阶段不新增、不升级 `package.json` 中的任何包。
- ECharts 按需引入：`echarts/core` + `BarChart` / `PieChart` + `CanvasRenderer` + `Tooltip` / `Grid` / `Legend`。
- 构建门禁固定为：

```bash
rm -rf dist && npm run build
```

> **原因**：本机安全策略会拦截构建时对旧产物的批量删除（chunk 数超过阈值），第二次直接 `npm run build` 必然失败。先清目录再构建是唯一稳定路径。

### 10.2 代码规范

- 组件文件 `PascalCase.vue`；api 函数 `camelCase`；路由 `kebab-case`。
- 统一 `<script setup>`；props 显式类型与默认值；样式一律 `<style scoped>`。
- 禁止 `console.log`、禁止遗留 `TODO`、禁止硬编码密钥。
- 不引 ESLint / Prettier（会新增依赖），以构建通过 + 代码评审兜底。

### 10.3 提交与协作

- 一批一提交：`feat(front): 商品列表分页与筛选`。
- 本阶段只改 `codes/frontend/**`；B0 可改 `design/**`；`AGENTS.md`、`package.json` 变更需用户确认。
- 提交前 `git status` 必须干净，不含 `dist/`、`node_modules/`。
- 改坏直接回滚到上一提交，不做"边修边补"。

## 12. 风险与应对

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| 契约缺失 | 高 | 字段返工，前端 / Mock / 后端三方不一致 | B0 先行；Mock 严格由契约派生；字段名唯一 |
| 契约未经真实后端校验 | 中 | 阶段 5 联调暴露字段偏差 | 冻结 v1.0 + 联调清单；变更走 §8.3 流程 |
| 前端复制状态机 | 高 | 违反 `AGENTS.md` §8，答辩被追问 | 只渲染 `actions[]`；`StatusTag` 仅展示 |
| 未提交的坏改动 | 高 | 回滚粒度失效，提交混入无关变更 | 开工前 `git status` 清零（X2） |
| Element Plus 全量 / 按需文档冲突 | 低 | 误加依赖、构建抖动 | 以 `AGENTS.md` 为准，本阶段不加 unplugin |
| 构建被安全策略拦截 | 中 | 第二次 build 必失败 | 固定 `rm -rf dist` 后再 build |
| 雪花 ID 精度丢失 | 高 | 详情页查不到数据 | 全链路字符串；Mock 用 19 位字符串；禁止 `Number(id)` |
| 图片 404 / 依赖外网 | 中 | 答辩现场白屏 | 本地占位图 + `el-image` fallback，不用 CDN |
| 页面多、半成品堆积 | 中 | 后期集中补四态 | 每批 build + 四态门禁，未过不进下一批 |
| 范围蔓延（退款 / 优惠券 / 评价） | 中 | 工期失控，评分点无收益 | 以 §4.2 范围外清单为准，需求变更先评估 |

## 13. 验收标准

### 13.1 全局完成定义（DoD）

1. `rm -rf dist && npm run build` 通过，`npm run preview` 可正常访问。
2. 19 个页面路由可达，刷新不白屏，404 兜底正常。
3. 每个列表页四态齐全（loading / empty / error / 正常），控制台 0 error。
4. 所有金额、ID 以字符串传输与展示；页面无浮点运算、无 `parseInt(id)`。
5. 订单动作按钮全部来自 `actions[]`，前端无状态判断分支。
6. 页面 ↔ 接口 ↔ 报告章节映射 100% 覆盖，Mock 接口集与契约一致。
7. 1440 / 1024 / 375 三档抽查无横向溢出（后台 1024 起，表格允许横向滚动）。
8. 每批一次提交，`git status` 干净；报告素材（截图、路由表、组件说明）随批产出。

### 13.2 验收记录方式

- 每批完成后在 `design/90-进度看板.md` 登记：批次、页面、接口编号、状态、备注。
- 缺陷与回归记录进 `design/60-测试与验收.md`，不在聊天里口头确认。
- 截图按 `docs-assets/阶段4/<页面>.png` 归档（不入库或按 `.gitignore` 约定处理）。
